**Count:** 1317 pytest + 605 vitest — **full suite green 2026-07-29** (owner-run), covering month close, the month pack, lira formatting and the exporter-import guard. The seven failures in that run's first pass were a stale local venv, not code; see the environment note below.

**Don't hold an entity-scoped ORM object across a `commit()`.** A commit expires loaded instances, so the next attribute read reloads the row — and if that read happens outside an `entity_context`, RLS hides it. SQLAlchemy finds nothing and raises `ObjectDeletedError`, which reads as "the row was deleted" when it is merely invisible. In tests, grab the id (`lock.id`) while the instance is still valid and carry the UUID. This cost a CI run on 2026-07-27; product code is safe because every path either reads inside the context or returns plain dataclasses.

**A function-local import is invisible to every other function.** `py_compile` only checks syntax, so a name imported inside function A and used in function B passes every static check and fails at runtime with `NameError`. Grepping the file finds the name and reads as a false OK — this cost three CI runs on 2026-07-29 (`CARD_COMMISSION_CODE`, then `JournalEntry`). Run `python3 scripts/scopecheck.py app/**/*.py` before handing over: it resolves each function's names against **module scope only**, so a local import elsewhere can't mask a missing one. Closures are the known false-positive class — a nested function reading its parent's variables is fine.

**Failures naming a third-party module are an environment problem until proven otherwise.** `No module named 'xlrd'` / `'sentry_sdk'` means the interpreter running pytest isn't the one the project was installed into — on macOS, usually a bare `python3 -m pytest` picking up the python.org build instead of `backend/.venv`. `pytest_sessionstart` in `tests/conftest.py` now compares the environment against `pyproject.toml` and stops with the fix. **Don't wave these away as "just my machine" without checking** — `xlrd` is a *runtime* dependency (legacy .xls bank statements), so the same gap in a deployment breaks a real feature. Production installs from `pyproject.toml` via `backend/Dockerfile`, and CI rebuilds a clean venv in `verify_fresh_install.sh`, so both are covered.

**Renaming a shared helper? Grep for the old name across `app/`, not just the file you're in.** Renaming `format_kurus_label` → `money_header` on 2026-07-29 left three exporters (POS, supplier activity, delivery) importing a name that no longer existed. `py_compile` passes — it never resolves imports — and no test imported those modules, so the whole suite stayed green while three download endpoints would have 500'd on first use. `test_excel_export.py::test_every_exporter_still_imports` now covers that family; the general lesson is that **an untested module is invisible to every check you run.**

**Grepping the calling syntax proves nothing about the data flowing through it.** Converting exports to lira, I checked my work with `grep "value=.*_kurus"` and declared it done. Four blocks wrote money through a loop variable — `for label, value in figures: ws.cell(value=value)` — and the grep couldn't see them. Verify the output, not the source: the guarding test loads the workbook and asserts what's in the cells.

**Calling a posting service directly? Pass `actor_id`.** Request schemas type it as `OptionalActorId = None` because the API fills it in (`resolve_actor_id` returns a UUID or raises 422). A test that calls the service directly reaches that `None`, and it fails at the **INSERT**, not at validation — first on `ledger_audit_events.actor_id`, since the journal entry is written before any subledger row. The error therefore names a table you weren't thinking about. This cost two CI runs on 2026-07-27.

**Registry-completeness guards — read this before adding a `JournalEntrySource`.** Several registries assert every enum member is classified and fail the suite if not. Adding a source means updating *all* of them in the same commit:
- `core/ledger/correction.py::verify_correction_source_registry_complete` — generic-correctable / dedicated route / void-and-re-enter
- `features/reports/cash_flow.py::verify_cash_flow_source_registry_complete` — operating / investing / financing / excluded / non-cash / opening-balance
- `frontend/src/lib/transaction-registry.ts` — `JOURNAL_SOURCES`, `SOURCE_FLOWS` (its own vitest asserts every non-system source maps to a flow page), and `GENERIC_VOID_SAFE_SOURCES` if the entry should be voidable from the General ledger

These caught `year_end_close` twice in 2026-07-27 — once server-side, once in the frontend. That is the guards working, but the cost is a failed run; check them up front.
